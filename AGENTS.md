# Tonnr

Tonnr is a free, open-source surf-conditions service. Users save spots with the conditions that make them work, get alerted when measurements or forecasts match, and share spots. An API serves the data underneath: buoy measurements, forecasts, tides, and history.

Read `docs/product-vision.md` before product work, `docs/data-sources.md` before touching a data provider, `docs/self-hosting.md` before changing how an instance is deployed, and the relevant record in `docs/decisions/` before structural work. Record a new decision there after making a durable one.

## Boundaries

- `apps/server` hosts the oRPC router with Hono on Node. It serves the API at `/v1`, with its spec at `/v1/openapi.json` and reference at `/v1/docs`, the typed RPC transport at `/rpc`, the MCP server at `/mcp`, and Better Auth at `/api/auth`. It deploys as a Docker container, and decision 009 says how.
- `apps/worker` fetches buoy data on a schedule and writes it to the database. Every three hours it looks at the alerts and writes what they tell, and every quarter of an hour it tells what begins and, at an account's hour, the evening before: `src/alerts.ts` and `src/moments.ts` read and write, and the rules are in `packages/conditions`. It also says that it is there and what each of its jobs last did, in two tables that the API reads and never writes: `src/runs.ts` does it around every job the scheduler runs, and decision 022 gives the rules. A new job is run through `attemptOf` in `src/index.ts` and listed there, or the page of the instance does not know it. Every three hours `src/pages.ts` fetches the forecasts of an eighth of the cells of the surf breaks whose page a search engine may list, on the pages' share of the budget, so that each page shows its week and no crawler has the provider asked: decision 057. It deploys as a second container, which applies the migrations at its start as the API's does. Each provider is one module that knows its provider's format and nothing about the database. Decision 004 describes the model. A provider that asks for a key is fetched only by an instance that holds it: `providersOf` in `src/ingest.ts` lists it then, and decision 032 gives the rules. A provider of wind names how often it measures in `packages/api/src/wind-places.ts`, which keeps one station for each place on the map and, on a wide view, the stations by the sea first: decision 048. `src/coast.ts` measures how far a station stands from the shore, from Natural Earth's coastline, as `src/store.ts` writes it. `src/breaks` adds surf breaks to the catalogue, once and by hand: from a file, or from a source it fetches, one module per source, and stores the candidates a list proposes, for the admin to decide (`candidates.ts`). Nothing there runs on a schedule. Decisions 024 and 049 cover it.
- `apps/web` is the TanStack Start app. It deploys to Cloudflare through `packages/infra`, one stage at a time. `prod` is production, at `tonnr.app`, and there is no pre-production: decisions 021 and 052.
- Product analytics is optional PostHog, defined in decision 044 and inventoried in `docs/analytics.md`. An action declares its `analytics` event in its oRPC metadata, and the common middleware captures it on success, server-side, without reading its input or output. The browser sends consent and technical IDs in dedicated headers, identifies by auth ID alone, and resets when the account changes. `Analytics` mounts on `/app` and `/login`: no SDK or layout-specific events on the landing. Umami counts the pages read on every page, the landing's too, from the root route, with no query and no consent: decision 055. Keep `app_active`, activation (`alert_created`), environments and the browser property allowlist consistent with the analytics document. Error reports go to the same project: from the browser under the same consent and on the same pages, and from the API as faults that name no one. `privateExceptionList`, in `packages/config/src/errors.ts`, is what a report keeps, for both: decision 054. Tests and CI send nothing.
- `apps/native` is the app for phones, for iOS and Android: Expo SDK 58 and expo-router, in development builds, never Expo Go (decision 069). It calls the API as the web app does, through the router's types imported as types from `@repo/api`, on `/rpc`, with `src/utils/orpc.ts`, which names the app in `expo-origin` and says its platform and build in `X-App`, and the API takes it as one of the instance's own clients by `APP_ORIGINS`. At run time it imports `@repo/config`, `@repo/client` and the modules of `packages/conditions` that read no file and ask no provider, and nothing else of the server's packages: `.oxlintrc.json` refuses the rest unless it is a type. Better Auth's Expo client keeps its session's cookie in the phone's keychain (`src/lib/auth-client.ts`, decision 070). Its theme is written from `packages/ui/src/styles/globals.css` into `src/theme/` by `pnpm --filter @repo/ui run native-theme`, which a test keeps current: a value of the theme is changed there and nowhere else. Its messages are the web app's, in `apps/web/messages/`, compiled by `scripts/messages.mjs`: a string only the app shows is a message there too, in every language. Its type is Geist, in `assets/fonts`, under the OFL. Its tabs are the platform's own, the four of decision 040, and the "+" is a tab that opens `src/app/create.tsx` and is never a screen. `ios/` and `android/` are written by `expo prebuild`, and Git ignores them: what they need is said in `app.config.ts` or a config plugin. The store's builds call Téo's instance alone, from `EXPO_PUBLIC_SERVER_URL`, fixed as they are built (decision 075).
- `apps/admin` is the app an operator runs the instance from: the developer accounts, their keys, the counts of calls, the accounts with their sessions, their suspension and their username, the spots their owners ask to make public, what accounts wrote of the breaks and the reports of the waves, with every check of each photo (decision 067) and what each was read and told (decision 068), which are the three kinds of its moderation, the catalogue of breaks, which an operator changes, merges and deletes on a map, with the candidates a list proposes to it, decided one at a time (decision 049, `src/components/catalogue/`), and the state of the instance, where an operator closes the web app to visitors and opens it again, turns its error reports off and on (decision 054), and stops the uploads of photos and videos and starts them again (decision 066). It is a second TanStack Start app at an address of its own, which the API learns from `ADMIN_ORIGIN`. It deploys to Cloudflare as the second app of a stage that names `ADMIN_DOMAIN`. It calls the API as the web app does and holds no logic of its own. Decision 020 says why it is not a part of `apps/web`.
- `packages/api` holds the procedures. Each user action is one oRPC procedure, and its validation, authorization, and logic live in that procedure. Every procedure asks who calls: an account, a key, the link of a shared list, which reads as a key does (decision 035), or a visitor of the web app or of the app for phones, who has no account and reads as a key does until an operator closes the instance to visitors, or demand is strong: `packages/api/src/visitors.ts` holds the number (decision 039). It is built on `callerProcedure` for the data everyone shares, `protectedProcedure` for what an account owns, `operatorProcedure` for what the instance keeps to its operator, or `adminProcedure` for what runs the instance, which also takes a request from the admin's site. A procedure built on it that changes something records the change with `recordAction`, in the same transaction. Only the two health checks are built on `publicProcedure`, the one that answers `OK` and `GET /v1/health`, which says since when the API and the worker run. `linkProcedure` takes no session either and is counted: only what a link does is built on it, in an alert mail or to a shared list, the name of a break or a station that its short address is shown with, what says whether the instance answers visitors, and which builds of its apps for phones it answers, `clients.get`, from the API's settings (decision 069). The console of decision 027 is built on `protectedProcedure`: what an account reads there is a developer account an operator made it a member of, and every query of it names the caller. A test walks every procedure and holds a new one to `adminProcedure`'s rules until it is named in one of the test's lists. Every one of them is counted, by hour, caller and outcome: the API keeps nothing else of a call. Decisions 019 and 020 give the rules. What asks the forecasts, `forecasts.get`, `alerts.preview` and a session that reads the sea, counts the question to its caller first, with `admitForecastQuestion` in `packages/api/src/forecast-callers.ts`: an account, a link or a visitor by its address, which `packages/api/src/address.ts` reads as the proxy says it, has so many an hour. A key is held to its developer account's limit instead. Decision 053. The public pages of the web app read `pages`, in `packages/api/src/routers/pages.ts`: what the page of a surf break says in one call, from the catalogue, the stations, the tides and the forecast that is kept, and the hubs and the addresses a sitemap names. Which breaks are listed is `standsAlone` in `packages/db/src/listed.ts`, with `standsAloneSql` saying the same to the database, for the API and for the worker alike. A break has the address of its page from the day it enters the catalogue, through `packages/db/src/addresses.ts`, and keeps it: a merge leaves it as an alias. Decision 057. What a phone shows outside its app reads `places.now`, in `packages/api/src/routers/places.ts`: the sea at twelve places at most, breaks, stations and spots, with the functions of `packages/api/src/pages.ts` and from what is kept, asking no provider. It answers a break and a station to any caller, and a spot to whoever reads it elsewhere, and counts one forecast question a call all the same: decision 074. The procedures of the API belong to a versioned router. Decision 003 says what may change inside a version. `V1_PROCEDURES`, in `packages/api/src/v1.test.ts`, names every procedure of `v1`: a new one adds its name there, and none is taken out (decision 069).
- `packages/api/src/mcp.ts` is the MCP server, what an agent lists and calls at `/mcp`: Streamable HTTP, with nothing kept between two requests. It takes an API key, or the token of an account that signed an assistant in, and gives a procedure the key, or that account, and nothing else: a cookie that comes with a request is not read. A token is made by the sign-in library, which `packages/auth/src/agents.ts` sets up as an authorization server, and read there too: a token says `read` and names no one, a client registers itself, and one read of the database at each request says whether the account still agrees and is not suspended. `packages/api/src/routers/agents.ts` lists an account's assistants and takes one back. Decision 047. A tool is a procedure that declares one under `mcp` in its metadata, with a description written for a model: the server lists those, says of each input what the reference says, and calls the procedure, which asks who calls, counts the call and checks the input. Nothing there reads the database but the door, `keyWorks`. A call that came by it is counted as its procedure's, with `mcp` as the way it came, which the context carries: `USAGE_WAYS` in `packages/db/src/schema/access.ts`. A tool marked `account` reads what an account keeps: it is listed to that account's assistant and to no key, and none writes. A new tool is a procedure a key may call, or one of the account's that reads: it is named in the list of `mcp.db.test.ts`, and said in `docs/mcp.md`, in `/llms.txt`, on `/agents` (`SHARED_TOOLS` and `ACCOUNT_TOOLS` in `landing-agents.tsx`, in every language) and in decision 045, in the same change.
- `packages/api/src/community.ts` holds the rules of what accounts write of a break, as functions that read no clock and no database: what a line takes, what a contribution counts for, the ranks, and the numbers an account is held to. The lines are `GUIDE_WORD_LINES` and `GUIDE_TEXT_LINES` in `packages/db/src/schema/community.ts`: a line of words is a column of `surf_break` with its words in `LINE_WORDS`, and a new one is given its reading in the web app, the admin and the public page in the same change, as `sizeFactors` and the one-sentence text `sizeNotes` were (decision 062). `src/guides.ts` reads a guide and confirms a contribution, and `src/standings.ts` computes a score, which nothing keeps, and writes a rank the day it is reached. The procedures are `guides`, which anyone reads as they read a break, `contributions`, which take an account with a username, `reviews`, an operator's, and `friends`, an account's link and the friends it made. An account made through a link has its owner as its sponsor: the sign-in library reads the link that comes with a sign-up, in `packages/auth/src/invitation.ts`, and an account that exists already becomes a friend and no more. `packages/db/src/friends.ts` holds what makes a friend and a sponsor, for both. A friend reads the other's username, rank and confirmed contributions, and no score. Who confirmed or contested a contribution is answered to no other account: it would tell which breaks an account keeps. What changes a contribution, a score or a friendship holds what it touches in one order and no other, or two requests at once stop each other: the accounts' rows first, with `holdAccounts` in `packages/db/src/accounts.ts`, then the line of the guide, with `holdLine`, then the contribution's row. A contribution never writes the catalogue: what was confirmed is laid over a break as it is read. Decision 041 gives the rules.
- `packages/db` holds the Drizzle schema and client. Use stock Postgres 18 features and change the schema through Drizzle migrations, so the database stays portable. Decision 001 gives the reason. It also holds `src/forecasts.ts`, the functions that keep a forecast in Postgres and count the requests for it: it knows the tables, and is told the rules.
- `packages/conditions` computes what the sea does at a point: tides, forecasts, and whether an alert's conditions are met at a spot. `src/alerts` holds the rules of an alert as functions that read no clock and no database: which hours an account can use, and what a look tells. Decision 031 gives them, and their tests are its detail. The API and the worker both use the package, and it knows nothing about HTTP or the database. A forecast is kept and its requests are counted through three functions that the program gives it: each program builds its `forecasts` once, with its share of the provider's budget, and passes them on. Decision 023 gives the rules. A test builds them with `testForecasts`, which asks no provider.
- `packages/conditions/src/sessions` holds what a session of an account's log comes to, as functions that read no clock and no database: the tide over it, `tideOver`, one figure for each thing the sea did at its middle, `sessionFigures`, and what an account likes at a place from the sessions it rated there, `likedConditions`, said as the conditions of an alert are, and how many times the height of the forecast the waves of a break run, from the sizes said in the sessions of every account there, `sizeFactor` in `size-factor.ts`, said once five sessions of two accounts gave a ratio and by the swell's sector and period when enough were in it: `breaks.sizeFactor` answers it as one figure and a count, and the break's panel says it in a sentence, `SizeAgainstForecast` in `apps/web/src/components/viewer/`, under the tiles, with what the guide's line `sizeFactors` says, and nothing when neither says anything. Decision 062. `packages/api/src/sessions.ts` reads what the sea did while a session lasted, once, as it is written: the models through `forecasts.over`, which answers the two days that are kept from the forecast in force and asks the provider for older days, and the stations in the database. The procedures are `sessions`, an account's alone. Decision 043 gives the rules.
- `packages/client` holds what the web app and the app for phones both run, as functions that read no React, no DOM, no phone and no database: the colors of the sea's scales, the units and how a measurement is written in them (`unitWriting`), how a figure, a bearing and a moment are written (`formatting`), the densities, the palettes and what was looked at last, the tabs of a phone, the words and the sliders of an alert's conditions (`alertWords`), the tide of its editor, the samples of the sea and a station's wind, and the types the screens read of the API. Each app gives it its messages, its language and its units in force, and keeps on its device what it keeps, with what draws it again. The web's modules re-export it from where it was, so that their imports did not change. A rule the two apps share goes there and nowhere else: `.oxlintrc.json` refuses there React, a platform, Node and an app's files, and the server's packages unless what is imported is a type. Decision 069.
- `packages/upstream` is how the API and the worker call a data provider. It sets the user agent, the timeout, and the retries, which never follow a 429, so no other code calls `fetch` on a provider.
- `packages/api/src/places.ts` finds a place by its name, to put a spot on the map. It asks the Photon the instance's settings name, within what it lets itself ask, and keeps and logs nothing of a search. Decision 030 gives the rules. A test builds it with `testPlaces`, which asks no service.
- `packages/api/src/routers/push.ts` keeps the browsers an account's alerts are pushed to. The address of a browser's subscription and its two keys come in a request's body, and go into no answer, no refusal and no log: a query of that file runs through `quietly`, which passes nothing of the database's words on, a device is named by a UUID and by nothing a caller could write, and the request's line in the log leaves out what stands where that id goes and is none. `subscribe` and `renew` hold the account's row first, then the caller's session, then the rows of `push_subscription`, `renew` in the order of their ids. A device is kept with that session and goes with it, by the database's own cascade, so that the API forgets a browser as its account signs out there. What changes a device takes the account its page acts for, and refuses a caller that is another. Decision 031, "Push", gives the rules.
- `packages/mail` is how the API and the worker send a mail: through the provider the instance's settings name, once, with nothing logged of a mail but how it failed. The API sends the mails of an account's own address, the one that checks it and the one that lets a forgotten password be replaced, and the ideas the landing's form and the messages of `/contact` send whoever makes the product, to `CONTACT_EMAIL` and twenty a day at most (`packages/api/src/ideas.ts`), and the worker the mails of the alerts, to an account that said yes and whose address is checked: `apps/worker/src/deliveries.ts` queues one with a notification and sends what is due, within an account's and the instance's mails for the day. A mail is written as it leaves, from what the alert holds then. Every mail is drawn with the pieces of `src/design.ts`, in the web app's light theme, and a new mail is too. A test sends none: `testMailer` keeps mails in memory. Decisions 026 and 031 give the rules.
- `packages/push` is how an instance sends a push to a browser: encrypted for that browser and signed with the instance's pair of keys, to an address that a push service of the browsers gave and to no other, once, with nothing logged of a push but how it failed. It is built on `node:crypto` and `node:https`, with no library: a push that is given up has its connection closed, which is why the request is its own. `isPushEndpoint` tells such an address from any other, for the API that takes one. `src/alerts.ts` writes what an alert's push says, in the words its mail uses: `packages/mail/src/alert-words.ts` holds them for both. The worker sends the pushes of the alerts, to every browser an account subscribed from: `apps/worker/src/deliveries.ts` queues a push beside a mail, each with a delivery of its own, and sends both by the same rules, each keeping what it told at a spot. What that file does for one way out it does for the other, or says why not. A test sends none: `testPusher` keeps pushes in memory, and reads them as their browser would. Decision 031, "Push", gives the rules. `src/reports.ts` writes what the push of a notice of reports says, which may carry a picture: decision 068.
- `packages/media` is how the API and the worker keep a photo or a video: the bucket, through files-sdk (`src/storage.ts`), and what the worker makes of a file, `src/photo.ts` with sharp and `src/video.ts` with ffmpeg, which reads one file, of a phone's or a browser's containers, and nothing it points to. A file goes from the browser to the bucket and never through the API: `media.prepare` signs where it goes with its type and its size, `media.uploaded` hears that it came, and the worker's job `process-media`, in `apps/worker/src/media.ts`, makes it, one at a time, and empties `media_trash`, which a trigger of the database fills whichever way a row of `media` goes. The API answers addresses of the bucket signed for the hour, the same all through it. The media of a session are read by `media.sessions`, its owner's alone, and are in no answer of `sessions`, whose procedures are tools of an assistant. An instance without its bucket keeps none, and the web app offers none. A test keeps files with `testStorage`, in memory. Decision 066. The media of a report at a break are checked by the same job: where and when they were taken, from the file (`src/metadata.ts`) or the phone, by the rules of `src/report-checks.ts`, which read no clock and no database, and what they show, by two open models that `src/analysis.ts` runs in the worker and `src/models.ts` pins, which the worker's image downloads as it is built and never as it runs. A test analyses with `testAnalyser`. The procedures are `reports`, in `packages/api/src/routers/reports.ts`. Decision 067. A report that is shown is told to the accounts that keep its break, in a notice that the reports of the next three hours join: the worker's job `tell-reports`, in `apps/worker/src/report-notices.ts`, writes it and pushes it once, holding what it holds in the order that file says, and `reportNotices`, apart from `notifications`, answers it. A browser counts each report it saw and opened once, which `reports.seen` and `reports.opened` keep as numbers its author reads. Decision 068.
- `packages/auth` sets up Better Auth, with what keeps a suspended account out, what sends the mails of an account's address, which check it and let the account choose a new password (`src/verification.ts`, decision 026), and the username, which is what others read of an account: the library's own plugin keeps it, in small letters and one account's alone, no account signs in by it or takes it off, and one that an operator took away is nobody's to take again (`src/username.ts`). `packages/config/src/username.ts` says what a username is, for the API and for the web app that checks one before it asks. Decision 041 gives the rules. `packages/ui` holds shared interface primitives.

## Interface

For UI work, follow `GUI.md` and use `graphical-ui`, `graphical-convert`, or `graphical-audit` from `.agents/skills/` as appropriate. Decision 014 says how the web app and the mobile app share a design.

- The Tonnr theme is defined once, in `packages/ui/src/styles/globals.css`. `gui/` is the snapshot it was written from, not a source to edit.
- `rounded-s`, `rounded-l`, and `max-w-xl` do not mean the theme's steps in Tailwind. The comment above `@theme` in that file gives the spelling to use. A component taken from the registry may use them: fix them when it comes in.
- `packages/ui` follows Téo's handbook (teogoulois.com/code/web/conventions). Primitives live in `src/components/ui/`, and each one is taken from the teogoulois registry, then given the Tonnr theme. Add a missing one the same way before writing a new one.
- Icons are Nucleo, imported from `@repo/ui/icon` and nowhere else. The theme's snapshot names another set: Nucleo replaces it. A new icon is taken from Nucleo Micro Bold, the package `nucleo-micro-bold`, which Téo asked for on 2026-10-13: what was taken from Nucleo UI before stays as it is until he says. The tiles of the landing take Nucleo UI fill duo, the package `nucleo-ui-fill-duo-18`, which he asked for on 2026-10-14. What a surf break is like is drawn in rings, as Stormrider's guides draw it, and Nucleo has none: `packages/ui/src/icon/surf-icons.tsx` draws them, to be read at 40 pixels with few marks, each from what it says, which Téo asked for on 2026-10-14. Each has two looks, Nucleo UI's Fill Duo, a disc at its second opacity with full shapes in its line, and a ring in a fine line: `SURF_LOOK` there says which a glyph takes, Fill Duo as Téo chose, and the design system shows both. A line of a guide, a break's or a spot's, is `CharacteristicRow` with `CharacteristicIcon`, in `apps/web/src/components/viewer/break-characteristics.tsx`: a word the catalogue gains is given its drawing there.
- `/design-system` shows every shared component with its variants and states, in development only. A new component is added there in the same change.
- The app for phones has its own kit, in `apps/native/src/components/ui/`: `Text`, `Button` and `IconButton`, `Chip`, `Segmented`, `Switch`, `Surface` and `Card`, `Separator`, `Section` and `Row`, `EmptyState`, `ErrorState`, `Skeleton`, the form sheet of `sheet.tsx` and `sheet-options.ts`, whose guard asks before what was written is lost, and `useTell`, its one toast. Each takes the theme in force from `useTheme`, in `src/lib/theme.ts`, which also keeps the theme a person chose on the phone, and a touch is felt through `feel`, in `haptics.ts`. `src/app/design-system.tsx`, at `app.tonnr://design-system`, shows each with its variants and states, in light and in dark, in development only: a new native component is added there in the same change. A screen takes its parts from the kit before HeroUI Native's or React Native's own.
- A short text that its reader changes by hand, such as a length under a slider, is written with `MorphText`, in `apps/web/src/components/shared/`: its figures move to what it becomes, on the theme's own motion, and stay still for a reader who asked for no motion. The library is Torph, which Téo chose: nothing else imports it.
- Charts are EvilCharts, copied into `packages/ui/src/components/evilcharts/` and given the theme. A screen draws a curve through `SeaChart` in `apps/web/src/components/viewer/`. The panel of a buoy or of a surf break is `Details`, in `apps/web/src/components/viewer/details/`. It shows the essentials, the details or everything, by the density the reader chose, which `apps/web/src/lib/density.ts` keeps in the browser and `preferences.getDisplay` and `preferences.saveDisplay` in the account, as the units are: the essentials are the sea now in a sentence, `SeaNow` in `details/sea-now.tsx`, judged by the place's own words with the rules of `packages/conditions/src/sea-now.ts`, and the days ahead in words, `DaysAhead`; the details are the panel without the energy, the swell apart, the gusts, the nearest buoy and the model beside the buoy; everything is the whole of it. A new part of the panel says which densities draw it, in `details.tsx`. `DensitySwitch` at the end of the panel goes one step down or up, and the account's panel has the line. Decision 061. A station that measures the wind alone gets `WindDetails` there: its wind and its gusts over hours or days beside the model's wind, with no tide, which the route then does not ask for. At a surf break or a spot, the wind is read on the nearest station that measured it lately, and named by how it meets the shore when the break's offshore bearing is known: `shoreWind` in `packages/conditions`.
- The guide of a surf break is `BreakGuide`, in `apps/web/src/components/guides/`: the second tab of a break's panel. A line says its value and who gave it, opens on what completes or corrects it, one line at a time, and shows what waits to be confirmed, with what an account that keeps the break may say of it. Three questions are answered by each account for itself. A visitor who presses a line is asked for an account and goes on to that line, and an account with no username chooses one there. The route answers it through `useGuiding`, in `apps/web/src/routes/app/-guiding.ts`, which also keeps what was typed and not sent while the app is open. What an account wrote and where it stands is `ContributionsPanel`, one step into the account's panel, `?panel=account&settings=contributions`, and a rank is written with `RankBadge`. `?tab=guide` opens a break's panel on its guide. Decision 041 gives the rules.
- An assistant that an account signs in sends it to `/connect`, which is `ConnectPage`, in `apps/web/src/components/auth/`: the account signs in there, is told what the assistant will read and the host its answer goes to, and allows or refuses. The API sends the query it signed after a `#`, so that no server reads it and the router, which writes a query its own way, leaves it alone: `apps/web/src/lib/agent-sign-in.ts` reads it once as the app starts, and gives it back to the API as it came. The account's panel lists its assistants and disconnects one: `useAgents`, in `apps/web/src/routes/app/-agents.ts`. Decision 047 gives the rules.
- An account's link and its friends are `FriendsPanel`, in `apps/web/src/components/friends/`, one step into the account's panel, `?panel=account&settings=friends`: the link with its code, which `QrCode` draws, and each friend with what they wrote. The short address `/i/<token>` leads to `?invite=<token>`, after the server has rendered it with a title that names whose link it is, for the sites a link is sent through, where `InviteDialog` says whose link it is over the map: a visitor is asked for an account, which the sign-up then makes through the link, and an account becomes a friend at its own word. The route answers both through `useFriends`, in `apps/web/src/routes/app/-friends.ts`. A link that comes while the instance is closed to visitors goes with the sign-up of `LoginWall`. Decision 041 gives the rules.

## The product name

The name may change. Read it from `APP_NAME` in `@repo/config/app` wherever a user sees it, and keep it out of identifiers. Packages use the neutral `@repo` scope for that reason.

To rename the product, change `APP_NAME`, then the name in `apps/web/public/site.webmanifest`, and the prose in `README.md`, this file, and `docs/`. `APP_SLUG`, the `name` in `docker-compose.yml`, and the `name` in the root `package.json` identify infrastructure. Change them only before the first deploy. `APP_SCHEME`, which names the apps for phones in the stores, never changes once an app is in one (decision 069). Compose names the images after its project, and `.github/workflows/ci.yml` starts the worker's by that name.

A list's own words are translated into them outside this repository, and what does not fit is kept in `surf_break_listing`, which the admin reads to its operator and nothing else reads. A break's description is its operator's own words, never a list's text: decision 049.
- Only a source whose terms allow it is fetched, and only when an operator asks: OpenStreetMap today. No collected list, and no sample of one, goes into the repository. A test reads invented breaks.

## Working with others

Other people and agents work on this repository from other machines, on `main`.

- Commit often, one change per commit, so that work in progress never sits only on one machine.
- Run `git pull --rebase` before starting a task and before each commit.
- Run `pnpm run check` before each commit, and `pnpm run format` when it names a file. A red `main` stops whoever deploys next.
- Push after each commit. The project is at an experimental stage, and `main` is where everyone meets.

## A public repository

The repository is public, and so is its history. Decision 012 says what follows.

- Keep secrets, personal data, and paths of one machine out of code, tests, docs, and commit messages.
- Tests and CI never call a data provider. A test reads a saved sample, as small as the test needs.
- CI reads one secret, the licence key of the icons, in the step that installs. A workflow that needs another is a decision to record first.
- What a deployment needs goes into `docs/self-hosting.md` in the same change: other people follow it.

## Environment files

Téo's rules are at teogoulois.com/code/workstation/secrets. In this repository:

- Each app's `.env.schema` declares its variables and is committed. Varlock validates them at startup and generates `src/env.ts`.
- Each app's `.env.example` lists the same variables with fake values. Update it in the change that starts reading a variable, and tell Téo which value goes in which file.
- Real values live in `apps/server/.env`, `apps/web/.env` and `apps/admin/.env`, which Git ignores. The worker and `packages/db` read the server's values through their schema's `@import`.
- `packages/infra/.env` holds the access to Cloudflare, and `packages/infra/.env.<stage>` the values of one stage of the web app, and of its admin app when it has one. Git ignores both, and `packages/infra/.env.example` shows them. Only `pnpm run deploy:web` and `pnpm run deploy:admin` read them.
- The `.env.example` at the root lists what `docker-compose.yml` and the commands that deploy the API and the worker read, and the licence key of the icons. `TEST_DATABASE_URL` is set in the shell and in CI, in no file.
- Show a file's variable names, never its contents. `envsync push` is Téo's to run.

## Commands

`package.json` lists the scripts. These have a catch:

- Localify serves the web app at `https://tonnr.localify` and the API at `https://api.tonnr.localify`. Start each with `localify dev web` and `localify dev server`: Localify picks the port. The local `.env` files name these two addresses, so the API's CORS and the auth cookies match them.
- The admin app starts with `pnpm run dev:admin`, on port 3002. The API answers it only when `ADMIN_ORIGIN` in `apps/server/.env` is the address the browser shows for it, and that address must share a site with the API's: `http://localhost:3002` beside `http://localhost:3000`, or `https://admin.tonnr.localify` beside `https://api.tonnr.localify`.
- `pnpm install` needs `NUCLEO_LICENSE_KEY` in its environment: the icon packages check the licence when they install, and stop the install without it. The root `.env` holds the key, and pnpm does not read that file: `export $(grep NUCLEO_LICENSE_KEY .env) && pnpm install`. Any pnpm command installs first when the dependencies changed, and stops the same way. The API's and the worker's images do not install them.
- `pnpm run check` runs lint, the format check, the type check, and the tests. It writes nothing, and stops at the first of the four that fails. CI runs the four as steps of their own, each whatever became of the others. `pnpm run format` writes.
- `pnpm run db:start` needs Docker.
- `pnpm run docker:up` runs the release images of the API and the worker with Postgres. It takes ports 3000 and 5432 unless `API_PORT` and `POSTGRES_PORT` name others, and belongs to the same Compose project as `db:start`, so stop the development API first.
- The tests that need Postgres are skipped unless `TEST_DATABASE_URL` names a server on which they may create databases: `TEST_DATABASE_URL=postgresql://postgres:password@localhost:5432/postgres pnpm run test`. Each creates a database of its own and drops it.
- The API listens on `PORT`, 3000 by default. To try something next to a running app, start a second one with `PORT` and `DATABASE_URL` set in the environment.
- `pnpm run dev` leaves the worker out, so that starting the app does not poll the providers. Start it with `pnpm run dev:worker`, or run one job once with `pnpm --filter worker run job <provider>`, `... job alerts`, `... job moments`, or `... job exposure`. `... job breaks <file>`, `... job breaks-fetch osm` and `... job breaks-remove <list>` are decision 024's commands, and `... job candidates <folder>` and `... job candidates-remove <list>` decision 049's. They write only with `--write`. So do `... job operator <account id>` and `... job operator-remove <account id>`, which name the operators of decision 019. `... job push-keys` makes the pair of keys an instance sends push with, prints it, and writes nothing.
- `pnpm run dev:native` starts Metro for the app. `pnpm --filter native ios:simulator [name]` builds the development build, installs it on an iPhone simulator and opens it on that Metro, which needs Xcode and CocoaPods: it builds with xcodebuild, unsigned and with `-packageAuthorizationProvider netrc`, since `expo run:ios` refuses an app that asks for push without a team to sign it, and Xcode otherwise waits for the keychain as it fetches MapLibre. iOS asks once whether to open the link in the app. And `pnpm --filter native android` on an emulator, which needs JDK 17 (`openjdk@17`, with `JAVA_HOME` set) and the Android SDK in `~/Library/Android/sdk`. A build is needed again only when a native module is added or `app.config.ts` changes: the rest reloads through Metro. `apps/native/.env` names the API the app calls: on the iPhone's simulator the Mac is `localhost`, on Android's emulator `10.0.2.2`, and a phone needs a tunnel. A trial API for it runs on a database of its own, never the one `apps/server/.env` names.
- `pnpm run deploy:api` and `pnpm run deploy:worker` ask Easypanel to build and restart a service of Téo's instance, from what is on `main`. Each calls the service's deploy address, a secret that lives in the root `.env` and nowhere in the repository. Each then waits until the new service has started, and fails when none did in ten minutes: it reads `GET /v1/health` at the address `DEPLOYED_API_URL` names in the same file, which says when the API started and when the worker that started last did, each with the commit its image was built from. The image reads it as it is built, through `scripts/revision.mjs`, from the three things of `.git` that `.dockerignore` lets in. `pnpm run deploy:status` reads the health and deploys nothing, and says whether what runs is `main`'s head. A deployment is checked by these, not by the API answering: Easypanel leaves the container before in place when a build fails. Decision 022 gives the rules.
- `pnpm run deploy:web <stage>` sends the web app to Cloudflare: `pnpm run deploy:web dev` for the pre-production. It builds what `main` holds on the remote, in a checkout of its own, so push first, and it never builds the working tree. It shows what it will change and asks. `--yes` skips the question, which a shell without a terminal needs, and `--dry-run` only shows. Deploy the API first when the web app needs something new from it. Do not run `alchemy deploy` yourself, because the command is what gives a stage its values. Do not change Alchemy's version without Téo either. Its state store in Cloudflare is shared with his other projects, and decision 021 says what a newer version does to it.
- `pnpm run deploy:admin <stage>` does the same for the admin app, for a stage whose file names `ADMIN_DOMAIN`. The API of that stage must already name the admin's address in `ADMIN_ORIGIN`: deploy the API first.
- Apply schema changes with `pnpm run db:generate`, then `pnpm run db:migrate`. `db:push` skips the migration files. Turborepo refuses these scripts in a shell without a terminal, as an agent's is: run them in the package, `pnpm --filter @repo/db run db:migrate`.
- Run `pnpm run auth:generate` after changing Better Auth plugins, and `pnpm run env:generate` after changing a `.env.schema`.
- tsdown bundles into `apps/server/dist` every dependency that `apps/server/package.json` does not list. A library that reads files next to its own module then fails at startup, so list it there, as `@neaps/tide-database` is.
- Varlock blocks any HTTP response that contains the value of a sensitive variable. Mark a variable `@public` in `.env.schema` when its value may appear in a response, as the server URL does in the OpenAPI spec.
