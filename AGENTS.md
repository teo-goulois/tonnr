# Tonnr

Tonnr is a free, open-source surf-conditions service. Users save spots with the conditions that make them work, get alerted when measurements or forecasts match, and share spots. An API serves the data underneath: buoy measurements, forecasts, tides, and history.

Read `docs/product-vision.md` before product work, `docs/data-sources.md` before touching a data provider, `docs/self-hosting.md` before changing how an instance is deployed, and the relevant record in `docs/decisions/` before structural work. Record a new decision there after making a durable one.

## Boundaries

- `apps/server` hosts the oRPC router with Hono on Node. It serves the API at `/v1`, with its spec at `/v1/openapi.json` and reference at `/v1/docs`, the typed RPC transport at `/rpc`, and Better Auth at `/api/auth`. It deploys as a Docker container, and decision 009 says how.
- `apps/worker` fetches buoy data on a schedule and writes it to the database. Every three hours it looks at the alerts and writes what they tell, and every quarter of an hour it tells what begins and, at an account's hour, the evening before: `src/alerts.ts` and `src/moments.ts` read and write, and the rules are in `packages/conditions`. It also says that it is there and what each of its jobs last did, in two tables that the API reads and never writes: `src/runs.ts` does it around every job the scheduler runs, and decision 022 gives the rules. A new job is run through `attemptOf` in `src/index.ts` and listed there, or the page of the instance does not know it. It deploys as a second container, which applies the migrations at its start as the API's does. Each provider is one module that knows its provider's format and nothing about the database. Decision 004 describes the model. A provider that asks for a key is fetched only by an instance that holds it: `providersOf` in `src/ingest.ts` lists it then, and decision 032 gives the rules. `src/breaks` adds surf breaks to the catalogue, once and by hand: from a file, or from a source it fetches, one module per source. Nothing there runs on a schedule. Decision 024 covers it.
- `apps/web` is the TanStack Start app. It deploys to Cloudflare through `packages/infra`, one stage at a time. `dev` is the pre-production, at `dev.tonnr.app`. Decision 021 describes the stages.
- `apps/admin` is the app an operator runs the instance from: the developer accounts, their keys, the counts of calls, the accounts with their sessions and their suspension, the spots their owners ask to make public, and the state of the instance, where an operator closes the web app to visitors and opens it again. It is a second TanStack Start app at an address of its own, which the API learns from `ADMIN_ORIGIN`. It deploys to Cloudflare as the second app of a stage that names `ADMIN_DOMAIN`. It calls the API as the web app does and holds no logic of its own. Decision 020 says why it is not a part of `apps/web`.
- `packages/api` holds the procedures. Each user action is one oRPC procedure, and its validation, authorization, and logic live in that procedure. Every procedure asks who calls: an account, a key, the link of a shared list, which reads as a key does (decision 035), or a visitor of the web app, who has no account and reads as a key does until an operator closes the instance to visitors, or demand is strong: `packages/api/src/visitors.ts` holds the number (decision 039). It is built on `callerProcedure` for the data everyone shares, `protectedProcedure` for what an account owns, `operatorProcedure` for what the instance keeps to its operator, or `adminProcedure` for what runs the instance, which also takes a request from the admin's site. A procedure built on it that changes something records the change with `recordAction`, in the same transaction. Only the two health checks are built on `publicProcedure`, the one that answers `OK` and `GET /v1/health`, which says since when the API and the worker run. `linkProcedure` takes no session either and is counted: only what a link does is built on it, in an alert mail or to a shared list, and what says whether the instance answers visitors. The console of decision 027 is built on `protectedProcedure`: what an account reads there is a developer account an operator made it a member of, and every query of it names the caller. A test walks every procedure and holds a new one to `adminProcedure`'s rules until it is named in one of the test's lists. Every one of them is counted, by hour, caller and outcome: the API keeps nothing else of a call. Decisions 019 and 020 give the rules. The procedures of the API belong to a versioned router. Decision 003 says what may change inside a version.
- `packages/db` holds the Drizzle schema and client. Use stock Postgres 18 features and change the schema through Drizzle migrations, so the database stays portable. Decision 001 gives the reason. It also holds `src/forecasts.ts`, the functions that keep a forecast in Postgres and count the requests for it: it knows the tables, and is told the rules.
- `packages/conditions` computes what the sea does at a point: tides, forecasts, and whether an alert's conditions are met at a spot. `src/alerts` holds the rules of an alert as functions that read no clock and no database: which hours an account can use, and what a look tells. Decision 031 gives them, and their tests are its detail. The API and the worker both use the package, and it knows nothing about HTTP or the database. A forecast is kept and its requests are counted through three functions that the program gives it: each program builds its `forecasts` once, with its share of the provider's budget, and passes them on. Decision 023 gives the rules. A test builds them with `testForecasts`, which asks no provider.
- `packages/upstream` is how the API and the worker call a data provider. It sets the user agent, the timeout, and the retries, so no other code calls `fetch` on a provider.
- `packages/api/src/places.ts` finds a place by its name, to put a spot on the map. It asks the Photon the instance's settings name, within what it lets itself ask, and keeps and logs nothing of a search. Decision 030 gives the rules. A test builds it with `testPlaces`, which asks no service.
- `packages/mail` is how the API and the worker send a mail: through the provider the instance's settings name, once, with nothing logged of a mail but how it failed. The API sends the mail that checks an account's address, and the worker the mails of the alerts, to an account that said yes and whose address is checked: `apps/worker/src/deliveries.ts` queues one with a notification and sends what is due, within an account's and the instance's mails for the day. A mail is written as it leaves, from what the alert holds then. A test sends none: `testMailer` keeps mails in memory. Decisions 026 and 031 give the rules.
- `packages/push` is how an instance sends a push to a browser: encrypted for that browser and signed with the instance's pair of keys, to an address that a push service of the browsers gave and to no other, once, with nothing logged of a push but how it failed. It is built on `node:crypto` and `node:https`, with no library: a push that is given up has its connection closed, which is why the request is its own. `isPushEndpoint` tells such an address from any other, for the API that takes one. `src/alerts.ts` writes what an alert's push says, in the words its mail uses: `packages/mail/src/alert-words.ts` holds them for both. The worker sends the pushes of the alerts, to every browser an account subscribed from: `apps/worker/src/deliveries.ts` queues a push beside a mail, each with a delivery of its own, and sends both by the same rules, each keeping what it told at a spot. What that file does for one way out it does for the other, or says why not. A test sends none: `testPusher` keeps pushes in memory, and reads them as their browser would. Decision 031, "Push", gives the rules.
- `packages/auth` sets up Better Auth, with what keeps a suspended account out and what sends the mail that checks an address. `packages/ui` holds shared interface primitives.

## Interface

For UI work, follow `GUI.md` and use `graphical-ui`, `graphical-convert`, or `graphical-audit` from `.agents/skills/` as appropriate. Decision 014 says how the web app and the mobile app share a design.

- The Tonnr theme is defined once, in `packages/ui/src/styles/globals.css`. `gui/` is the snapshot it was written from, not a source to edit.
- `rounded-s`, `rounded-l`, and `max-w-xl` do not mean the theme's steps in Tailwind. The comment above `@theme` in that file gives the spelling to use. A component taken from the registry may use them: fix them when it comes in.
- `packages/ui` follows Téo's handbook (teogoulois.com/code/web/conventions). Primitives live in `src/components/ui/`, and each one is taken from the teogoulois registry, then given the Tonnr theme. Add a missing one the same way before writing a new one.
- Icons are Nucleo, imported from `@repo/ui/icon` and nowhere else. The theme's snapshot names another set: Nucleo replaces it.
- `/design-system` shows every shared component with its variants and states, in development only. A new component is added there in the same change.
- Charts are EvilCharts, copied into `packages/ui/src/components/evilcharts/` and given the theme. A screen draws a curve through `SeaChart` in `apps/web/src/components/viewer/`. The panel of a buoy or of a surf break is `Details`, in `apps/web/src/components/viewer/details/`. A station that measures the wind alone gets `WindDetails` there: its wind and its gusts over hours or days beside the model's wind, with no tide, which the route then does not ask for. At a surf break or a spot, the wind is read on the nearest station that measured it lately, and named by how it meets the shore when the break's offshore bearing is known: `shoreWind` in `packages/conditions`.
- A direction is written with `Bearing`, in `apps/web/src/components/viewer/bearing.tsx`: an arrow that points the way the wind or the swell goes, then the name of the point it comes from. Never a name alone. A chart of a panel asks `useChartTurn` in `chart-turns.ts` before it draws: it waits for its drawer to come to rest, then for its turn, so that drawing it never stops a drawer that moves.
- A wave height and a wind speed have one color each, defined in `apps/web/src/lib/sea-scales.ts`. The sea, the markers, the legend, and the charts read it there.
- A measurement is written in the unit its reader chose: a wind speed, a height, a temperature, a distance and a rain each have a function for it in `apps/web/src/lib/units.ts`, such as `formatWind` and `formatHeight`. The screens compute in knots and in the metric units, as the scales of colors do, and a component that writes a measurement calls `useUnits` so that it is drawn again when a unit changes. The choices are made in `UnitsSettings`, in `apps/web/src/components/shared/`, and kept in the account by `preferences.getUnits` and `preferences.saveUnits`. Decision 033 gives the rules.
- A panel of the map opens in `ViewerDrawer`: beside the map on a wide screen, as a sheet at the bottom of a phone.
- A spot of the user's own is added from `NewSpotPanel`, in `apps/web/src/components/spots/`. While it is open the map selects nothing: a press puts the spot's marker, through `onPlace` on `StationMap`. Decision 006 says what a spot is saved with.
- What the owner of a spot does with it is one menu, `SpotActions` in `apps/web/src/components/spots/spot-menu.tsx`: rename or move it (`SpotEditor`, with the marker of `NewSpotPanel`), ask that it be made public, delete it. A spot says under its name that it is private, or what became of the request. Decision 034 gives the rules.
- A list is shown alone on the map by `?list=<id>`, and a list opened by its link by `?shared=<token>`, which opens while the instance is closed to visitors too: the short address `/l/<token>` leads there. The map then draws that list and nothing else, and its panel is `ListPanel`, in `apps/web/src/components/lists/`, beside `ShareListDialog`, which shares a list. An account goes from one list to another, and back to everything, by `ListChips`, the row of chips at the top of the saved panel, and finds a list by its name in the command palette. The route opens a link through `useSharedList`, in `apps/web/src/routes/app/-shared.ts`, and every address it navigates to keeps the list. Decision 035 gives the rules.
- An alert is written in `AlertEditor`, in `apps/web/src/components/alerts/`: one sentence whose parts open what changes them, in the third tab of the panel of a spot of the user's own. That tab lists the spot's alerts with `SpotAlerts`, since a spot may have several, and what an alert asks is said in a line by `AlertSummary`. The parts that ask something of the tide draw it with `AlertTideChart`. What is written there and not saved is held in `apps/web/src/lib/unsaved.ts`: whatever is about to take the editor's place leaves through its `leaveWith`, which asks first, and the route's blocker does the same for a navigation. The alerts panel lists what was told, the alerts, and the account's settings. The route answers all of them through `useAlerting`, in `apps/web/src/routes/app/-alerting.ts`. Decision 031 gives the rules.
- Keyboard shortcuts are listed in `apps/web/src/lib/shortcuts.ts` and registered through its `useShortcut`, never with a `keydown` listener. The user can rebind each one, so read the binding in force from `useShortcuts` when showing it.
- `Mod+K` opens the command palette, in `apps/web/src/components/shared/command-palette.tsx`. A new page or primary action is added there in the same change.
- `/` is the landing page and `/app` is the product. A screen under `/app` is a component that takes props, in `apps/web/src/components/<feature>/`, and its route loads the data.
- Before `/app` knows who opens it, it shows `AppPending`, in `apps/web/src/components/shared/`: the real bar and `ViewerSkeleton`, in `apps/web/src/components/viewer/`, which draws the map's place with its buttons, its legend and its timeline where the viewer puts them. The server sends it, since it does not render `/app`, and a step that waits before the map shows it too, never a spinner. What moves in the viewer's layout moves there in the same change.
- `/app` takes whoever comes, with an account or without. A visitor reads the map, and what needs an account asks for one through `useAuthPrompt`, in `apps/web/src/components/auth/auth-prompt.tsx`. While the instance is closed to visitors, the layout of `/app` shows `LoginWall`, in the same folder, in place of the map: `apps/web/src/routes/app/route.tsx` asks the API before it draws, and `isClosedToVisitors` in `apps/web/src/lib/visitors.ts` knows the refusal of an instance that closed since. Decision 039 gives the rules.
- Every string a user reads is a message in `apps/web/messages/en.json` and `fr.json`. English has no URL prefix, French lives under `/fr`. Paraglide generates `apps/web/src/paraglide/`, which Git ignores.
- The admin app has its own messages, in `apps/admin/messages/`, and one address for both languages: a cookie keeps the operator's choice. It is built for a wide screen first, with the same theme and the same components. Its shortcuts are listed in `apps/admin/src/lib/shortcuts.ts` and registered through its `useShortcut`, as the web app's are, and they belong to the browser: an account keeps a copy of the web app's alone. `Mod+K` opens its command palette, in `apps/admin/src/components/shared/command-palette.tsx`, where a new page or primary action is added in the same change. An account that is no operator gets the console of decision 027 there, under `/console`, outside the operator's routes: it has the same bar with a palette and shortcuts of its own, in the same files, and nothing of an operator's is mounted for it. A layout of the admin learns who is signed in through `signedIn` in `apps/admin/src/lib/guard.ts`, which drops what the page loaded when the account is no longer the one that loaded it.

## The product name

The name may change. Read it from `APP_NAME` in `@repo/config/app` wherever a user sees it, and keep it out of identifiers. Packages use the neutral `@repo` scope for that reason.

To rename the product, change `APP_NAME`, then the name in `apps/web/public/site.webmanifest`, and the prose in `README.md`, this file, and `docs/`. `APP_SLUG`, the `name` in `docker-compose.yml`, and the `name` in the root `package.json` identify infrastructure. Change them only before the first deploy. Compose names the images after its project, and `.github/workflows/ci.yml` starts the worker's by that name.

## Data rules

- Fetch from the upstream providers listed in `docs/data-sources.md`.
- Store each station's license and attribution, and return them in API responses.
- The catalogue of breaks, `surf_break`, holds what the instance's operator added to it, by hand and once: decision 024. It also holds the spots their owners asked to make public and an operator accepted, under the ODbL and with no account named: decision 034. A spot is otherwise its owner's alone, and one thing answers it to anyone else: a list that holds it, shared by its link (decision 035). A break's source and licence may be null, and the API then answers null: never write one that the list did not give.
- What a break is like is said in the words listed in `packages/db/src/schema/spots.ts`. A list's own words are translated into them outside this repository, and what does not fit is kept in `surf_break_record`, which no procedure and no scheduled job reads.
- Only a source whose terms allow it is fetched, and only when an operator asks: OpenStreetMap today. No collected list, and no sample of one, goes into the repository. A test reads invented breaks.

## Working with others

Other people and agents work on this repository from other machines, on `main`.

- Commit often, one change per commit, so that work in progress never sits only on one machine.
- Run `git pull --rebase` before starting a task and before each commit.
- Run `pnpm run check` before each commit, and `pnpm run format` when it names a file. A red `main` stops whoever deploys next.
- Push after each commit. The project is at an experimental stage, and `main` is where everyone meets.

## A public repository

The repository is public, and so is its history. Decision 012 says what follows.

- Keep secrets, personal data, and paths of one machine out of code, tests, docs, and commit messages.
- Tests and CI never call a data provider. A test reads a saved sample, as small as the test needs.
- CI reads one secret, the licence key of the icons, in the step that installs. A workflow that needs another is a decision to record first.
- What a deployment needs goes into `docs/self-hosting.md` in the same change: other people follow it.

## Environment files

Téo's rules are at teogoulois.com/code/workstation/secrets. In this repository:

- Each app's `.env.schema` declares its variables and is committed. Varlock validates them at startup and generates `src/env.ts`.
- Each app's `.env.example` lists the same variables with fake values. Update it in the change that starts reading a variable, and tell Téo which value goes in which file.
- Real values live in `apps/server/.env`, `apps/web/.env` and `apps/admin/.env`, which Git ignores. The worker and `packages/db` read the server's values through their schema's `@import`.
- `packages/infra/.env` holds the access to Cloudflare, and `packages/infra/.env.<stage>` the values of one stage of the web app, and of its admin app when it has one. Git ignores both, and `packages/infra/.env.example` shows them. Only `pnpm run deploy:web` and `pnpm run deploy:admin` read them.
- The `.env.example` at the root lists what `docker-compose.yml` and the commands that deploy the API and the worker read, and the licence key of the icons. `TEST_DATABASE_URL` is set in the shell and in CI, in no file.
- Show a file's variable names, never its contents. `envsync push` is Téo's to run.

## Commands

`package.json` lists the scripts. These have a catch:

- Localify serves the web app at `https://tonnr.localify` and the API at `https://api.tonnr.localify`. Start each with `localify dev web` and `localify dev server`: Localify picks the port. The local `.env` files name these two addresses, so the API's CORS and the auth cookies match them.
- The admin app starts with `pnpm run dev:admin`, on port 3002. The API answers it only when `ADMIN_ORIGIN` in `apps/server/.env` is the address the browser shows for it, and that address must share a site with the API's: `http://localhost:3002` beside `http://localhost:3000`, or `https://admin.tonnr.localify` beside `https://api.tonnr.localify`.
- `pnpm install` needs `NUCLEO_LICENSE_KEY` in its environment: the icon packages check the licence when they install, and stop the install without it. The root `.env` holds the key, and pnpm does not read that file: `export $(grep NUCLEO_LICENSE_KEY .env) && pnpm install`. Any pnpm command installs first when the dependencies changed, and stops the same way. The API's and the worker's images do not install them.
- `pnpm run check` runs lint, the format check, the type check, and the tests. It writes nothing, and stops at the first of the four that fails. CI runs the four as steps of their own, each whatever became of the others. `pnpm run format` writes.
- `pnpm run db:start` needs Docker.
- `pnpm run docker:up` runs the release images of the API and the worker with Postgres. It takes ports 3000 and 5432 unless `API_PORT` and `POSTGRES_PORT` name others, and belongs to the same Compose project as `db:start`, so stop the development API first.
- The tests that need Postgres are skipped unless `TEST_DATABASE_URL` names a server on which they may create databases: `TEST_DATABASE_URL=postgresql://postgres:password@localhost:5432/postgres pnpm run test`. Each creates a database of its own and drops it.
- The API listens on `PORT`, 3000 by default. To try something next to a running app, start a second one with `PORT` and `DATABASE_URL` set in the environment.
- `pnpm run dev` leaves the worker out, so that starting the app does not poll the providers. Start it with `pnpm run dev:worker`, or run one job once with `pnpm --filter worker run job <provider>`, `... job alerts`, `... job moments`, or `... job exposure`. `... job breaks <file>`, `... job breaks-fetch osm` and `... job breaks-remove <list>` are decision 024's commands. They write only with `--write`. So do `... job operator <account id>` and `... job operator-remove <account id>`, which name the operators of decision 019. `... job push-keys` makes the pair of keys an instance sends push with, prints it, and writes nothing.
- `pnpm run deploy:api` and `pnpm run deploy:worker` ask Easypanel to build and restart a service of Téo's instance, from what is on `main`. Each calls the service's deploy address, a secret that lives in the root `.env` and nowhere in the repository. Each then waits until the new service has started, and fails when none did in ten minutes: it reads `GET /v1/health` at the address `DEPLOYED_API_URL` names in the same file, which says when the API started and when the worker that started last did, each with the commit its image was built from. The image reads it as it is built, through `scripts/revision.mjs`, from the three things of `.git` that `.dockerignore` lets in. `pnpm run deploy:status` reads the health and deploys nothing, and says whether what runs is `main`'s head. A deployment is checked by these, not by the API answering: Easypanel leaves the container before in place when a build fails. Decision 022 gives the rules.
- `pnpm run deploy:web <stage>` sends the web app to Cloudflare: `pnpm run deploy:web dev` for the pre-production. It builds what `main` holds on the remote, in a checkout of its own, so push first, and it never builds the working tree. It shows what it will change and asks. `--yes` skips the question, which a shell without a terminal needs, and `--dry-run` only shows. Deploy the API first when the web app needs something new from it. Do not run `alchemy deploy` yourself, because the command is what gives a stage its values. Do not change Alchemy's version without Téo either. Its state store in Cloudflare is shared with his other projects, and decision 021 says what a newer version does to it.
- `pnpm run deploy:admin <stage>` does the same for the admin app, for a stage whose file names `ADMIN_DOMAIN`. The API of that stage must already name the admin's address in `ADMIN_ORIGIN`: deploy the API first.
- Apply schema changes with `pnpm run db:generate`, then `pnpm run db:migrate`. `db:push` skips the migration files. Turborepo refuses these scripts in a shell without a terminal, as an agent's is: run them in the package, `pnpm --filter @repo/db run db:migrate`.
- Run `pnpm run auth:generate` after changing Better Auth plugins, and `pnpm run env:generate` after changing a `.env.schema`.
- tsdown bundles into `apps/server/dist` every dependency that `apps/server/package.json` does not list. A library that reads files next to its own module then fails at startup, so list it there, as `@neaps/tide-database` is.
- Varlock blocks any HTTP response that contains the value of a sensitive variable. Mark a variable `@public` in `.env.schema` when its value may appear in a response, as the server URL does in the OpenAPI spec.

# This is NOT the Turborepo you know

Turborepo configuration, task behavior, and CLI commands can vary between installed versions and may differ from your training data. Resolve the `turbo` package from this file's directory or relevant workspace; in monorepos, it may not be visible from the repository root. For example, run `node -p "require.resolve('turbo/package.json')"` from a workspace that depends on `turbo`.

Read `docs/README.md` inside that installed package first, then read the relevant pages from its `docs/` directory before changing Turborepo configuration or commands. Heed deprecation notices. These bundled docs match the installed package version and are available without network access.

This block is written and re-added by `turbo` before repository-scoped commands when an AI agent is detected. In the Turborepo source repository, its template is defined in `crates/turborepo-cli/src/cli/agent_guidance.rs`. Removing the managed block while updates are enabled means a later qualifying invocation will add it again. Set `"agentGuidance": false` in the root `turbo.json` or `turbo.jsonc` to opt out; this does not remove an existing block. Keep the block committed with your work to avoid an uncommitted change on the next agent invocation.
